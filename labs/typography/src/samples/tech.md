给一篇文章配照片，最容易忽略的是第二次打开它的时候。第一次访问只需要回答“文件在哪里”，第二次却多了一个问题：浏览器手里的那份文件，还算不算数？把这两个问题分开，静态博客的发布过程就容易检查了。

## 一张图片，从草稿到读者的屏幕

写作时，在 Markdown 里保留相对路径。这样换一台电脑打开草稿，照片依然跟着文字走。发布时再读取图片的实际字节，计算 SHA-256 摘要，把它的一部分写进文件名。即使两次裁切的照片都叫作“窗外”，浏览器也能根据地址认出它们是两份内容。

> 地址一旦进入文章，就成了读者手里的一张取件凭条。重新编辑时，旧凭条仍然应该能取到当时那张照片。

### 为什么从内容计算摘要

假设两位作者同时修改图注，其中一位还调整了照片的白平衡。单靠编辑时间，构建器很难知道哪一份图片应该重新上传。按内容求摘要以后，只编辑图注的人会得到原来的文件名，调整颜色的人会得到新名字。同步器可以据此跳过已经存在的对象，失败后也可以从头重试。

下面的命令保留在同一行，窄屏可以在代码区内横向阅读。复制到终端时，仍然是一条完整的命令。

```text
curl --head --header 'Origin: https://qians.day' https://site-cdn.qians.day/posts/01K00000000000000000000000/test-27e984fd8dc5.webp
```

浏览器收到响应后，还需要根据资源类型决定如何解码。能看到状态码 200，只说明服务器找到了这个地址。如果响应正文其实是一个 HTML 错误页面，解码照片仍会失败。检查时把类型、大小和状态码摆在一起，比只看绿色的状态灯更容易发现问题。

## 把下载与复用分开记录

| 访问阶段 | 要观察的信号 | 所回答的问题 |
| --- | --- | --- |
| 初次打开 | 编码后的正文大小 | 首屏需要下载多少数据 |
| 再次打开 | 实际传输字节 | 是否从浏览器缓存复用 |
| 更换图片 | 新旧资源的地址 | 读者是否能看到新版本 |

表格里的两种大小有不同的含义。响应体经过压缩后，传输的字节通常会少一些；请求本身的协议开销又会增加一些。若想让下次测试可以复现，记录工具、页面地址、网络条件和采样时机，比只留下一个小数点后两位的数字更重要。

### 换一种设备再读一遍

在大屏幕上，代码和说明文字通常能肩并肩放进视野。到了手机上，阅读顺序变得更重要：先交代这个命令在查什么，再展示命令本身，最后解释返回值。这样即使手指只往下滑，也能跟上文章的推理。长表格则应保留列之间的对应关系，让需要比较的读者可以在表格内部移动。

文章收尾时，可以把照片重新裁小一点，观察旧地址和新地址分别返回什么。一次成功的请求只检验了眼前的一条路径，编辑、回退和重复打开才构成读者真实经历的一次发布。写下这些细节，是为了下一个接手草稿的人也能自己验证。

## 一份可以重读的访问记录

第一次做这个实验时，我只截了一张网络面板的图。几天之后再打开它，已经分不清那次访问是在编辑器里预览，还是在构建完成后打开了静态页面。两者看起来很像，可是前者会为调试加载额外的脚本，后者使用的才是准备交给读者的文件。于是第二次我把正在阅读的文章地址、窗口的宽度和构建时的内容版本写在同一行，让每一次测量都有来处。

还有一个很容易忽略的细节：点回上一篇文章，未必会发起一次新的导航。浏览器有时直接恢复已经画好的整个页面，连滚动位置都原样保留。这样的返回很快，对读者当然是好事，但它回答不了字体缓存是否有效的问题。要观察后者，需要让浏览器重新解析文档，确认它认出了样式表里的那些地址，然后再看哪些资源真的穿过了网络。

### 留下失败时的那一页

有一回，照片下面的说明已经出现，图片却迟迟看不见。我把同一个地址贴进新标签页，照片立刻打开，于是猜想是刚才的网络太慢。后来才发现测试稿漏写了高度，图片解码之前，下面的文字占了本该留给照片的空间。等图片出现，读者正在看的句子一下子被推到屏幕外。仅仅确认文件能打开，完全看不出这个问题。

后来我养成一个习惯：先读到一段话的中间，记住视口上边缘的那一行，再让资源慢慢到齐。如果还看得见同一句，继续读下去大概不费力；如果整段已经跑掉，就回头查是哪一个盒子的大小发生了变化。浏览器记录的位置变化可以补上数字，人的眼睛则能说明那一点移动究竟落在标题、正文还是一块空白上。把这两件事同时记下来，下一次修正时才知道往哪里看。

最后再回到写作本身。缓存命中了多少次，读者通常不会知道；但他会记得手指松开以后那一行字还在原地，也会记得夜里翻到一张明亮的照片，下面的说明有没有紧跟上来。这些看似琐碎的检查，最后都落在同一件事上：让已经坐下来读一篇文章的人，可以顺顺当当地把它读完。
